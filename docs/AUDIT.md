# Weapon Fitness — Master Audit

**Date:** 2026-06-10
**Sources:** 16 specialist audit slices in `docs/audit/raw/` (every finding below traces to a slice; file:line citations are from those slices). Live secret values (API keys, tokens, DB passwords) are never reproduced — referenced by type + location only. Hardcoded default/placeholder passwords (WF-008, WF-068) are quoted verbatim only where the literal value is itself the finding.

---

## 1. Executive summary

Every backend dependency of this app is dead: the Supabase project hosts resolve NXDOMAIN, the hardcoded ngrok tunnel that is the sole mobile API base URL is offline, and the FastAPI backend, Node email server, and Supabase Edge Function have no reachable deployment — so **nothing in this product currently works end-to-end**. Worse, the frontend actively hides this: attendance check-ins return fake "Offline Mode" success, the nutrition dashboard renders hardcoded fake totals, and the "AI" food scanner returns the same three fabricated meals for any photo — so any visual QA pass is testing fiction. The feature surface is genuinely broad (auth, multi-branch management, attendance, workouts, diet, nutrition, sleep, gamification, payments, groups, email, push, 3D anatomy, food scanning), but almost every feature is partial, internally inconsistent, or provably broken in code independent of the dead backends. Security is catastrophically broken: the FastAPI backend has **zero authentication on all 82 routes (46 of them mutations)**, the frontend never sends an Authorization header anywhere (the `useAuth` flag exists but is passed by zero call sites), and the Edge Function performs 15 admin-level actions with the service-role key while explicitly trusting client-supplied IDs ("for this refactor I will trust the payload"). Privilege escalation is trivial in at least three independent ways: client-settable `role` on profile create/update, the Edge Function silently upgrading any user to Trainer, and hardcoded default passwords ("trainer123" for every trainer created through the admin UI; "12345678" as the Edge Function's create-user fallback and the owner-signup script's literal — receptionist passwords are admin-chosen but never strength-validated). Live secrets are committed to git — `server/.env` with Brevo/SMTP keys, a Postgres superuser password hardcoded in `backend/app/core/database.py` plus 11 tracked scripts, and SMTP credentials shipped inside the client bundle via `expo.extra` — all of which require rotation and git-history scrubbing, not just deletion. The data layer cannot be rebuilt from the repo: Alembic has no `alembic.ini`, the two existing migrations contradict the models (the payments migration creates a table with only an `id` column), and 12 tables exist only because ad-hoc scripts mutated production directly. Data integrity is gamed-by-design: attendance uses a static spoofable QR string, a "Simulate Check-in (Dev)" button ships in production, XP is farmable through log churn, and a single trainer absence permanently corrupts a group's recurring schedule. On the web build — the only platform that currently boots — `Alert.alert` is a no-op, which silently kills all 146 feedback and confirmation call sites, meaning Delete User, Delete Group, Delete Plan, Admin Logout, and every login error simply do nothing. The UI has good bones (a consistent theming pattern in ~55 files, decent error-boundary strategy, some genuinely polished dark-mode visuals) but light mode is unusable, accessibility is literally zero, and the flagship trainee screen hardcodes 117 dark color literals on top of the theme system. The repo itself is a swamp: ~95 tracked junk files including 140KB of stashed screen copies, 362KB file listings, committed stack traces with real user UUIDs, and a debug screen wired into the production navigator. The honest verdict: this is a feature-rich prototype that was developed live against a now-deleted production database, with security and data integrity deferred everywhere; the rebuild must treat the backend as new work, preserve the better frontend patterns identified in §4, and fix the secrets exposure before anything else.

## 6. Design & UI quality summary (input for the redesign)

**The concrete patterns making the UI bad:**

1. **Web feedback is dead.** 146 `Alert.alert` call sites across 29 files are literal no-ops on react-native-web, plus 13 bare browser `alert()` sites — three competing feedback patterns, two of them broken or off-brand. Every destructive confirm (Delete User/Group/Plan, Admin Logout, Mark Absent) can never execute on web. The single highest-leverage design-system deliverable is a web-safe `ConfirmDialog` + `Toast` with an Alert-shaped adapter (ui-quality WF-019).
2. **Hardcoded color density.** Top offenders: TraineeHomeScreen 66 hex + 51 rgba; TrifectaDashboard 36 hex; OwnerDashboard 27; WorkoutAvatar 14+7; NutritionTrackerModal 14; TestScreen 14; AdminProfileScreen/LevelUpModal/FoodCameraScanner.web 13 each. Seven files import no theme at all (RankDashCard, FoodCameraScanner + FoodCameraScanner.web, Anatomy3DScene, TestScreen, WorkoutAvatar.web, SectionHeader).
3. **Theme system structurally broken.** `typography` tokens bake `color: darkColors.text` at module load; 17 files import the static dark palette (including ALL entry screens and all five tab navigators), so light mode renders white-on-light text and permanently dark chrome. Two design systems coexist (fully-themed files vs hardcoded Netflix-red gamification cards), plus a dead third palette (`constants/colors.js`, zero importers) and a third brand red in the splash config. At least 3 different "accent reds" are in use (#E50914, #FF4D4D, rgba(255,23,68,…)).
4. **No states.** No skeleton component exists anywhere; no toast/snackbar in legacy code. The flagship TraineeHomeScreen fires ~8 fetches with zero loading UI; TrainerDashboard, ReceptionistDashboard, TodayAttendanceScreen, ReceptionQRCodeScreen have no loading/error UI at all; errors are swallowed to console, leaving "loading", "empty", and "broken" visually identical.
5. **No system in type or space.** 21 distinct fontSize literals (incl. 7px and 9px below the legibility floor); 25 distinct spacing literals where the four most common values (10, 12, 20, 15 — used 566 times combined) are not on the theme's own scale. `spacing` is imported by only 12 of 67 files.
6. **Zero accessibility.** 0 accessibilityLabel, 0 accessibilityRole, 0 hitSlop across all 67 UI files; icon-only touchables throughout.
7. **Duplication as a design risk.** Five profile screens ~85% identical with drifted bugs; AnatomyView native/web ~95% duplicated and already diverged; five tab bars copy-pasted; modal shells diverge on every axis — overlay opacity 0.5/0.6/0.65/0.7/0.75/0.85, border radii 8-32, animation fade vs slide, and text-on-accent guessed three different ways (#FFF, #000, colors.primary) such that a theme switch breaks contrast in half of them. A shared `<AppModal>` would collapse ~60% of the modal layer.
8. **Monoliths.** TraineeHomeScreen (1,942 lines), OwnerDashboard (1,941), AdminDashboard (1,121) — with hook-using components declared inside render bodies, module-scope `Dimensions.get`, Platform.OS safe-area hacks, and `.map()` lists inside ScrollViews (no virtualization anywhere).
9. **Debug surfaces shipped.** "Test Backend Connection" on the landing page → TestScreen (14 hex, dumps BASE_URL + raw JSON); "Simulate Check-in (Dev)" on the trainee home; "3D Avatar Disabled for Checking" placeholder on web; AI-comment debris and emoji copy throughout.

**What the design system must provide (mechanical fix list, from ui-quality):** semantic color tokens + hex→token codemod map; color-free typography with `<Text variant>`; 4px-grid space tokens + codemod table; web-safe ConfirmDialog/Toast; AsyncContent/Skeleton/EmptyState/ErrorState; Button/IconButton with enforced 44px targets + required labels; Input with focus ring/error slot/keyboard presets; Screen wrapper with real safe-area insets; Modal/Sheet with keyboard avoidance; useWindowDimensions-based responsive helpers. Note: a new `theme/` + `components/ui/` system was being authored concurrently with this audit (untracked at audit time) — verify `App.js`'s imports of `./components/ui/Toast` and `./theme` resolve before anything else.

## 8. Cross-cutting risks & open questions (deduped)

1. **RLS status is the linchpin and is unverifiable.** 152 direct `supabase.from()` calls across 24 tables (profiles 38, branches 13, payments 12…) depend entirely on RLS policies that exist (or don't) only in the dead project. No policy definitions are committed anywhere in the repo. Any rebuild must author RLS as code. (security-sweep, components-modals-2, screens-dashboards)
2. **Edge-function `verify_jwt` is unknown.** No `supabase/config.toml` is committed, so the deployment default applies — and even if enabled, it only requires *some* valid JWT, not the right role. Combined with WF-003, exploitability hinges on this single unverifiable setting. (security-sweep, infra-email)
3. **Three competing data planes with no canonical owner.** Writes go via (a) the FastAPI backend, (b) direct client Supabase table access, and (c) the edge-function gateway — often for overlapping tables. The migration even proves the frontend and backend disagree on the attendance schema itself (`check_in_time` vs `attendance_date`), and `trainee_plan` is writable only by the client. **Decide which backend is canonical before fixing anything else.** (backend-data, components-modals-1/2, screens-dashboards, security-sweep)
4. **Is the FastAPI backend deployed anywhere, or superseded by the edge function?** No deployment evidence exists; if it ships, it must not ship without auth. Related: where did the Alembic config live when migrations were "applied" — i.e., how was the prod schema actually built? (security-sweep, backend-data)
5. **Has duplicate per-day data already inflated prod XP?** consistency_service counts raw rows and no per-day unique constraints exist; any revival of the old data needs a dedupe + XP audit first. (backend-data, backend-services)
