# Audit — backend-services (backend/app/services/, 14 files, 1312 LOC)

## Purpose

The service layer of the FastAPI backend: food-photo "AI" detection (vision_service), two in-process APScheduler jobs registered in backend/main.py:70-92 (sleep reminders, workout reminders), Expo push delivery, XP/level gamification, daily/weekly "trifecta" consistency tracking, trainee/trainer absence handling with workout-shifting, attendance-driven auto workout logs, motivation quotes, and thin CRUD helpers for profiles/trainers/branches.

## What actually works

- gamification_service XP/level math is internally consistent: `get_xp_for_level` (100·(L-1) + 50·(L-1)(L-2)/2) matches its documented table (L2=100, L3=250, L4=450, L5=700) and `calculate_level` is a correct inverse; `get_trainee_gamification_stats` self-heals a stale stored level (gamification_service.py:63-68).
- workout_reminder_scheduler correctly matches hour/minute and a comma-separated `days_of_week` allowlist, falls back to a generated motivational message, and wraps the whole run in try/except + finally db.close() (workout_reminder_scheduler.py:9-66).
- consistency_service's weekly milestone recount is recalculated from scratch (idempotent) rather than incremented (consistency_service.py:89-121); streak logic correctly detects date gaps (260-288).
- push token upsert (push_notification_service.py:116-139) and the Expo HTTP payload shape are correct.
- motivation_service is simple and fine.

## UI & design notes

- The food scanner, if surfaced in UI, presents fabricated certainty: "Egg" from a sports ball, fixed 300-kcal "Unknown Meal", `confidence` of the max box. Any nutrition UI built on this is decorative.
- "Trifecta" wording (likely shown in the consistency UI) is wrong for a four-part requirement.
- `progress` from gamification stats can exceed user expectations: weekly averages cap at 100% at 5 days, so the dots row (7 days) and the percentage disagree visually.

## Dead code & hygiene

- Entirely dead: vision_service.py (no route imports it — heavy `ultralytics`/`opencv` deps exist only for it), branch_services.py (empty), profile_services.py, trainer_service.py, async `send_expo_push_notification`.
- backend/ root is littered with ~40 one-off debug/fix scripts and captured JSON/log outputs (debug_*.json, uvicorn_*.log, files.txt — a venv listing from a *different machine*, `C:\Users\CHAYA\...`), confirming no requirements.txt: dependency set (apscheduler, ultralytics, httpx, requests) is only recoverable from files.txt.
- `print()` is the only logging mechanism in all 14 files; trainee UUIDs and message contents go to stdout every minute.

## Cross-slice questions

1. **backend-api slice**: does any router expose a food-scan endpoint that was *supposed* to call `vision_service.detect_food`? The frontend may have a scanner screen pointing at a route that 404s.
2. **backend-api slice**: do POST /attendance and the absence endpoints commit the session themselves? attendance_service.handle_absence adds an Attendance row without committing (relies on shift_workout_to_tomorrow's commit at workout_service.py:140 — which is skipped when there are no workouts to shift, line 81-83: confirm the row isn't silently lost there; `get_db` dependency teardown behavior decides).
3. **frontend slice**: does the workout UI deduplicate template-vs-WorkoutSchedule entries, or do users actually see the doubled workouts the shift comments warn about (workout_service.py:104-112)?
4. **db slice**: is `WorkoutReminder.days_of_week` stored as full English day names ("Monday,Tuesday")? The scheduler's `strftime("%A")` comparison breaks for any other format/locale.
5. **db slice**: confirm `ConsistencyProgress.trifecta_met` column default (None vs False) — affects the false→true XP transition on freshly inserted rows.
