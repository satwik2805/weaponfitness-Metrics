# Audit: components-modals-1

Files: AddBranchModal.js, AddReceptionistModal.js, AddTraineeModal.js, AddTrainerModal.js, AddWorkoutModal.js, AttendanceCalendarModal.js, BroadcastEmailModal.js, CreateDietPlanModal.js, CreateGroupModal.js, DietPlanModal.js, DietTemplatePreviewModal.js, FeedbackModal.js, FormLibraryModal.js (13 files, ~3,447 lines, all read in full).

## Purpose

The first half of the modal layer: staff-facing "create entity" modals (branch, receptionist, trainee, trainer, workout template, diet template, trainee group), trainee-facing consumption modals (attendance calendar, assigned diet plan viewer, diet template preview, trainer feedback, exercise form library), and an owner broadcast-email composer. They are the primary write surface of the app: three distinct backend paths are used — (a) the Supabase Edge Function `rate-limit-demo` with an `action` discriminator (`AddBranchModal`, `AddReceptionistModal`, `AddTrainerModal`, `FeedbackModal`), (b) direct client-side Supabase table writes (`AddTraineeModal`, `AddWorkoutModal`, `CreateDietPlanModal`, `DietPlanModal` reads), and (c) the FastAPI backend via `apiRequest` (`CreateGroupModal`). `BroadcastEmailModal` is a dumb form that delegates to an `onSend` prop (presumably wired to the Brevo `server/`).

## What actually works

The theming discipline is genuinely good: every modal uses `useTheme()` + `useMemo(createStyles)` with consistent `colors.card / inputBackground / border / accent` tokens, so dark/light theming is uniform. The edge-function error-unwrapping idiom (`funcError.context.json()` → `body.error`) is correctly copy-pasted in all four edge-function callers, so server error messages do surface. `AddTraineeModal` has the most complete validation in the family (trim checks, email regex, plan + payment-mode required) and a `finally`-guarded loading flag. `AttendanceCalendarModal`'s month math (first-day offset, leap-safe `new Date(y, m+1, 0).getDate()`, year rollover) is correct. `FormLibraryModal` is a polished, self-contained static feature with a sensible web/native split for video embeds. `CreateDietPlanModal` correctly chains library → meals → items inserts using returned PKs (`diet_library_id`, `diet_meals_id`).

## UI & design notes

- Overlay opacity is different in nearly every modal: 0.5 (Feedback), 0.6 (AddTrainer, Broadcast), 0.65 (AddBranch, AddReceptionist, AddTrainee, AddWorkout, CreateGroup, DietTemplatePreview), 0.7 (AttendanceCalendar), 0.75 (CreateDietPlan, DietPlan), 0.85 (FormLibrary). Same for border radii (8/10/12/14/16/18/20/22/32) and animation types (fade vs slide). A shared `<AppModal>` shell would collapse ~60% of these files.
- Text-on-accent color is guessed three ways: `#FFF` (AddBranch, AddReceptionist, AddTrainer, Broadcast, Feedback), `#000` (AddTrainee, AddWorkout, CreateGroup, CreateDietPlan), and spinner colors that contradict the text color in the same button (AddBranchModal.js:104, AddReceptionistModal.js:134).
- Loading affordance is inconsistent: spinner-replaces-label (AddBranch/AddReceptionist), spinner-replaces-button (AddTrainer), label-text-swap (AddTrainee/AddWorkout/CreateGroup/CreateDietPlan/Feedback), opacity dim only in Feedback. None visually disable the button besides Feedback.
- DietPlanModal.js:292 hardcodes `#ccc` for the description, illegible in a light theme.
- FormLibraryModal is the only modal with static (non-themed) StyleSheet + inline color overrides — works, but diverges from the `createStyles(colors)` convention.
- AttendanceCalendarModal `boxSize=42` × 7 = 294px + padding; fine on phones, but on web wide layouts `space-between` stretches gaps oddly.

## Dead code & hygiene

- `checkRateLimit` imported-unused in 7 files (see LOW finding) — the entire client-side rate-limiting idea was abandoned mid-migration to the edge function.
- AddReceptionistModal.js:35-47 dead `createAuthUser`; :61-62 duplicated `setLoading(true)`.
- AddTrainerModal.js:15 unused service imports; uses a different icon package than the rest of the app.
- AddTraineeModal duplicates the edge function's `add_trainee` action (rate-limit-demo/index.ts:713) entirely client-side — one of the two implementations is dead-by-intent and they will drift.
- Debug `console.log` in submit paths of 4 modals.
- File/export name mismatch `DietPlanModal.js` / `TraineeDietModal`.

## Cross-slice questions

1. **Edge-function slice**: confirm rate-limit-demo/index.ts:101 uses the client-sent `x-action-path` as the rate-limit key with no server-side derivation, and confirm the function validates the *caller's* role (it receives admin-level actions like `add_branch` from any authenticated — or anonymous? — client). Also confirm the `"12345678"` fallback password at index.ts:388.
2. **Backend slice**: does FastAPI `/trainee-groups/` POST validate the bearer token at all, given CreateGroupModal sends none? Does it verify `trainerId` against the token subject?
3. **Schema/nutrition slice**: does `diet_items` actually have `calories/protein/carbs/fats` columns (DietPlanModal.js:108-111 reads them; CreateDietPlanModal never writes them)?
4. **Screens slice**: which parents pass `onSend` to BroadcastEmailModal, and do they await/report Brevo failures? Which parents open FeedbackModal without `trainerInfo`?
5. **Modals-2 slice**: check whether the `Alert.alert`-on-web no-op and the `useAuth`-missing `apiRequest` patterns repeat there (they almost certainly do).
