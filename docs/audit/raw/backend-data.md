# Audit slice: backend-data

Scope: `backend/app/db/` (base, enums, types, all 17 model files), `backend/app/schemas/` (all 16 files), `backend/app/core/` (config.py, database.py), `backend/alembic/` (env.py, both version files). 38 files read in full.

## Purpose

This slice is the persistence layer of the FastAPI backend: SQLAlchemy declarative models for ~23 tables (profiles/branches/trainers/trainees, memberships, payments, attendance x2, sleep, workouts/templates/groups/schedules, diet library, nutrition logging, gamification consistency tracking, push tokens, reminders), the Pydantic request/response schemas the routers use, the engine/session factory pointing at Supabase Postgres, and an Alembic setup that nominally version-controls the schema.

## What actually works

The core identity graph (profiles → branches → trainers → trainees) is modeled coherently with sensible FK `ondelete` behavior (CASCADE for child rows, SET NULL for soft links, RESTRICT on branch owner). The custom `GUID` TypeDecorator (db/types.py) is a correct, cache-safe portability shim. Most child tables consistently use `GUID` PKs with `uuid.uuid4` defaults and timezone-aware `server_default=func.now()` timestamps. `NutrientGoal.trainee_id` and `PushToken.trainee_id` correctly carry `unique=True`. Pydantic schemas consistently use `from_attributes` and Create/Update/Response separation. `alembic/env.py` is correctly structured (imports models, `compare_type=True`). The first migration (3a92e031fe53) is hand-written, ordered correctly around the profiles↔branches circular FK, and matches the core models reasonably well.

## Dead code & hygiene

- Dead: `app/db/enums.py` ReportTypeEnum + DayEnum (never imported), the db/enums.py payment enums (shadowed by payment.py locals), `app/core/config.py` (zero importers), `app/schemas/enums.py` (empty), `app/schemas/init.py` (misnamed).
- The backend root is littered with ~40 one-off prod-mutation scripts (`fix_consistency_schema.py`, `migrate_gamification.py`, `create_*_tables.py`, `force_db_sync.py`, debug JSON dumps, uvicorn logs). These are the real "migration history" of the database and explain how 12 unmigrated tables exist. They belong in `_archive/` after their effects are captured in a baseline migration (Phase 5 candidate).
- `app/db/models/workout_schedule.py` and `consistency_progress.py` exist but are excluded from the package `__init__` — half-integrated.

## Cross-slice questions

1. **backend-routers**: Do any update endpoints call `payload.model_dump()` WITHOUT `exclude_unset=True` on `TraineeUpdate`? If yes, the xp=0/level=1 reset (MEDIUM above) escalates to HIGH/CRITICAL data corruption.
2. **backend-routers**: Confirm payments router accepts client-supplied `id` and `profile_id` with no auth check — combines S3 IDOR with client-generated financial PKs.
3. **frontend-data**: The frontend reads/writes `trainee_plan`, `attendance`, `custom_trainee_weekly_workouts` directly via Supabase JS while the backend ORM owns overlapping tables — map exactly which tables are dual-written; `attendance.check_in_time` (migration) vs `attendance_date` (model) suggests frontend and backend disagree on the attendance schema itself.
4. **backend-services**: consistency_service counts raw rows for trifecta/streaks — verify whether duplicate per-day rows (no unique constraints) have already inflated XP in prod data.
5. **infra**: Confirm no alembic.ini exists outside the repo (deploy host) — if migrations were ever applied, where did the config live?
